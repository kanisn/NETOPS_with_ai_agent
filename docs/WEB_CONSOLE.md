# 웹 실행 콘솔

NetOps Studio는 브라우저에서 실행 조건을 고르고, 실행 중의 Agent/MCP/A2A 활동을 보고, 종료 후 실제 실행 artifact에 근거한 분석을 여는 UI입니다. 프로젝트 폴더에서 `.\ccs.ps1 web`을 실행하면 기본적으로 이 컴퓨터 안에서만 접속할 수 있습니다. 처음 실행하거나 무료로 확인할 때는 [초보자 빠른 시작](QUICKSTART.md)을 같이 보세요.

## 서버 시작과 경로 선택

```powershell
# 로컬 브라우저로 열기. OS가 비어 있는 port를 고릅니다.
.\ccs.ps1 web --port 0

# 화면을 자동으로 열지 않고 접속 URL만 출력
.\ccs.ps1 web --port 0 --no-browser

# 웹 문서 목록·실행목록 등 관리 상태를 특정 workspace에 보관
.\ccs.ps1 web --port 0 --workspace 'D:\Codex\WorkingFiles\ccs-testbed\web'
```

`--port 0`은 기본값이며, OS가 비어 있는 port를 배정합니다. 터미널에 `Web console:`로 시작하는 URL이 표시됩니다. 브라우저 자동 열기가 꺼졌다면 그 URL을 같은 PC에서 직접 여세요. URL에는 이번 서버 instance의 capability token이 포함되므로 접속 링크 전체를 password처럼 취급하고 공개 문서나 issue에 복사하지 않습니다. 이 안내의 예시에는 실제 token이 들어 있지 않습니다.

웹 workspace는 **문서 library, 선택된 Runbook/Memory, Delay 제어값과 실행목록 index**를 보관합니다. 실행 결과를 보관하는 경로와는 다릅니다. workspace 선택 순서는 다음과 같습니다.

| 우선순위 | 설정 | 기본 동작 |
|---:|---|---|
| 1 | 명령행 `--workspace` | 이 실행에서 지정한 경로 |
| 2 | 환경변수 `CCS_WEB_WORKSPACE` | 따로 지정한 web library/control 경로 |
| 3 | 환경변수 `CCS_WORKING_ROOT` | 지정한 작업 경로 아래 `web/` |
| 4 | 환경변수 없음 | 저장소 루트의 `local-data/web/` |

`CCS_WEB_WORKSPACE`와 `CCS_WORKING_ROOT`의 PowerShell 설정법은 [초보자 빠른 시작](QUICKSTART.md#3-작업-위치-정하기)에 있습니다. 같은 문서 목록과 web 실행 index를 이어 보려면 이전과 동일한 workspace를 사용합니다. 새 workspace를 지정하면 새 관리 index를 사용합니다. 기존 workspace와 그 안의 항목은 보존하세요.

실행 산출물은 `configs/system.xml`의 `paths.output_root` 아래 `<run_id>/`에 저장됩니다. 공개 기본 설정은 `local-data/runs/`입니다. `--workspace`는 이 결과 경로를 바꾸지 않습니다. CLI에서만 쓰는 `run --output-root`는 그 CLI 실행의 경로 override입니다. `--system-config`를 지정하면 해당 XML의 `output_root`가 적용됩니다. run이 시작되면 해당 run의 결과 위치와 입력 snapshot이 고정되므로 이후 설정을 바꾸어도 진행 중인 run을 다른 폴더로 옮기지 않습니다.

## 포트 bind 문제

포트가 점유되었거나 OS가 접속을 거부하면 `could not bind`와 socket error가 표시될 수 있습니다. 우선 `--port 0`을 사용하거나 지정 포트를 다른 빈 포트로 바꾸세요. bind가 실패했다고 프로젝트 폴더 권한을 바꾸거나 다른 시스템 프로세스를 종료하지 마세요.

## LAN에서 접속 허용하기

LAN 접속은 localhost보다 노출 범위가 넓으므로 필요한 경우에만 켜세요. 다음은 설명용 RFC1918 사설망 예입니다. `192.168.1.10`을 서버 PC의 실제 사설 IPv4 주소로, `192.168.1.0/24`를 허용할 client subnet으로 바꿉니다. `/24`보다 좁은 대역, 예를 들어 한 기기만 허용하려면 그 PC의 `/32`를 씁니다.

```powershell
.\ccs.ps1 web --no-browser --port 8765 --host 192.168.1.10 --allow-network 192.168.1.0/24
```

LAN에서는 서버가 client IP, 허용 CIDR, 요청의 `Host`, POST의 same-Origin, per-process token을 확인합니다. 허용할 client 대역은 `/24`보다 넓을 수 없고 wildcard bind는 거부됩니다. 이 예는 암호화되지 않은 HTTP이므로 신뢰할 수 있는 사설 LAN에서만 사용하고 인터넷으로 공개하지 마세요. Windows Firewall inbound rule이 필요한 경우 서버 PC의 관리자 PowerShell에서 다음처럼 특정 주소와 port를 허용합니다. 이 예는 `8765`가 비어 있고 Windows 네트워크 프로필이 Private일 때를 가정합니다. port를 바꾸면 rule의 port도 맞춥니다.

```powershell
New-NetFirewallRule -Name "CCS-NetOps-LAN-8765" -DisplayName "CCS NetOps LAN 8765" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 8765 -LocalAddress "192.168.1.10" -RemoteAddress "192.168.1.0/24" -Profile Private
```

`Ctrl+C`를 누르면 서버가 종료됩니다. 브라우저 탭만 닫는 것은 서버를 종료하지 않습니다.

## 실행 설정 → 실시간 모니터링 → 결과 분석

NetOps Studio는 흰색 카드와 여백 중심으로 정리한 세 탭을 제공합니다. **실험 시작**을 누르면 모니터링으로 이동하고, 실행계의 마무리가 끝나 분석 자료가 준비되면 **결과 분석**으로 자동 이동합니다. 저장된 결과를 다시 볼 때는 최근 실행의 **보기** 또는 결과 분석의 실행 선택기를 사용합니다. 결과 화면의 **진행 기록 보기**는 해당 실행의 모니터링으로 돌아갑니다.

설정 화면에서는 시나리오·요청과 지식 조건이 중심이며, 호출 상한·승인 정책 등은 **고급 실행 옵션**에서 조정합니다. 긴 Runbook/Memory 목록은 각 카드의 **문서 관리** 창으로 분리했습니다. 입력 중인 문서 내용과 선택한 언어는 화면 갱신 때문에 초기화되지 않습니다.

모니터링의 큰 구조도에는 운영자, 운영 에이전트, 진단 에이전트, Runbook 검색, Incident Memory, Network Tools가 있습니다. 요청·보고·검색·Memory·진단 위임/반환·MCP 경로마다 색이 있으며, **화살표와 해당 로그가 같은 색**을 사용합니다. 실제 진행 중인 작업의 세부 모듈만 점등합니다. 실행 전체를 감싸는 Runner 시작 기록은 작업 중인 세부 모듈로 표시하지 않습니다.

세부 모듈은 운영 에이전트의 컨텍스트/조치/승인/보고, 진단 에이전트의 조사/근거/결론, Runbook의 검색/결과, Memory의 조회/초안/저장, Network Tools의 조회/미리보기/적용/검증/롤백입니다. 노드·화살표·로그를 선택하면 연결된 경로와 원본 상세를 확인할 수 있습니다. 선택한 과거 기록의 강조와 실제 진행 중인 작업의 점등은 구분됩니다.

실행 설정에서 다음 값을 바꿀 수 있습니다.

| 옵션 | 의미 |
|---|---|
| Mock / Live | Mock은 유료 API를 호출하지 않습니다. Live는 기존 설정의 실제 모델과 API Key를 사용하고 누적 예산을 적용합니다. |
| Model Profile | `ai.local.xml`에 등록된 Profile을 선택합니다. 키 내용은 웹에 전달하지 않습니다. |
| 장애 시나리오 / Seed / 반복 | W1–W5/N0, 난수 Seed, 같은 incident의 반복 수를 선택합니다. 기본값은 W4와 첫 Seed, 1회입니다. |
| 난이도 | L1/L2/L3 합성 시나리오 조건입니다. |
| 운영자 요청 | 비워 두면 시나리오의 기본 요청을 사용합니다. |
| RAG / Memory | Runbook 검색과 Memory 읽기·쓰기를 각각 켜고 끕니다. |
| Top K | Runbook과 Memory가 반환할 최대 검색 결과 수입니다. |
| 승인 정책 | 자동 승인 또는 변경 거부를 선택합니다. |
| 고급 실행 옵션 | Diagnosis 도구 예산, Operation context 단계 수, Agent 단계 상한입니다. |

실행은 한 번에 한 개이며, 실행 중 문서 목록은 고정됩니다. Delay는 별도로 실시간 변경할 수 있습니다. 실행을 중지하면 대기를 해제하고 종료 처리를 요청하며, 중단된 실행의 부분 기록을 보존합니다.

## Runbook과 Memory 조건 바꾸기

- **문서 관리 → 문서 추가**: 제목과 본문을 입력하거나 Runbook `.md/.txt`, Memory `.md/.txt/.json` UTF-8 텍스트 파일을 선택합니다. 여러 파일도 선택할 수 있습니다. PDF나 Word의 자동 추출 기능은 포함하지 않습니다.
- **체크박스**: 다음 실행에 포함할 문서를 선택합니다. 선택하지 않은 문서는 검색 대상에서 빠집니다.
- **보기**: 문서 원문을 확인합니다.
- **제거**: 웹 실험 목록에서 문서를 제외합니다. 원본 파일과 과거 실행의 복사본은 보존합니다.
- **Memory 전체 비우기**: Memory 관리 창에서 웹 Memory 목록 전체를 비웁니다. 이전 run의 Memory DB·활동·보고서는 삭제하지 않습니다.

문서가 0개여도 실행할 수 있습니다. RAG OFF, Memory OFF와 문서가 없는 조건은 구별해 기록합니다. 실행마다 선택한 Runbook, 초기 Memory, 입력 조건과 hash를 run 내부 `inputs/` 및 manifest에 저장합니다.

직접 넣은 Memory는 **운영자가 제공한 검증되지 않은 참고 문서**로 표시합니다. 실제 Agent가 검증·승인 후 작성한 incident Memory와 출처를 구분합니다. 완료 run에서 생성된 승인된 Memory는 웹 목록에 추가되어 다음 실행에서 선택할 수 있습니다. 다시 입력으로 선택된 문서는 이전 결과를 포함한 참고 자료이며, 현재 장애를 다시 조회하고 검증해야 합니다.

## Force Delay

실행 설정의 **시연 대기 시간(Force Delay)**은 각 activity log를 기록한 뒤 다음 실행 동작으로 넘어가기 전에 기다릴 시간입니다. 화면의 로그 재생 속도만 바꾸는 기능이 아닙니다. Runbook 조회, Agent 판단·전달, MCP 실행/결과 등 각 활동 기록에 적용하므로 한 도구 호출 안에서도 여러 번 기다릴 수 있습니다.

모니터링 탭에는 다음 조작이 있습니다.

1. **Force Delay 입력창**: 0–30초를 입력합니다. 소수도 사용할 수 있습니다.
2. **적용**: 진행 중인 실행에 반영합니다. 이미 기다리는 중이면 변경된 값에 맞춰 남은 대기를 다시 판단합니다.
3. **현재 적용값**: 서버가 적용한 값을 표시합니다.
4. **No Delay**: 0초로 설정해 진행 중인 강제 대기도 해제합니다.

종료 기록과 중단 정리에는 추가 대기를 넣지 않습니다. 장시간 Delay로 정상 MCP/A2A 요청이 만료되지 않도록 웹 실행의 통신 timeout에 유한한 여유를 더합니다. 모델 API 자체의 설정 timeout과 비용 예산은 유지합니다.

## 항상 표시되는 네트워크 상태

상단의 네트워크 요약은 세 탭과 독립적으로 항상 표시됩니다. 활성 알람·설정 이상·처리량과 주요 변경을 보여주며, **상태 자세히**에서 설정·KPI·알람·조치 기록 전체와 초기 상태 선택기를 열 수 있습니다.

- 실행 전에는 선택한 시나리오/첫 Seed/난이도의 **초기 상태**를 보여줍니다. 여러 장애를 선택한 경우 패널의 시나리오 선택기로 초기 상태를 따로 확인할 수 있습니다.
- 실행 중에는 현재 episode의 실제 SQLite network state를 조회합니다. 이 관찰이 Agent에 정답을 전달하거나 망 상태를 수정하지는 않습니다.
- 설정값과 기준값, 활성 알람 수, KPI, network state version, topology 항목과 적용된 조치를 표시합니다.
- **초록색**은 기준 상태로 회복된 변경, **주황색**은 변경 또는 이상 상태입니다. 변경값에는 직전 값도 함께 표시합니다. 초기 조건이나 episode가 바뀌면 강조 기준을 다시 잡습니다.
- 빠른 실행으로 중간 화면을 놓친 경우에도 실제 change 기록을 이용해 변경된 설정을 강조합니다. DB 준비 중에는 상태 준비 중으로 표시합니다.

이 패널은 현재 구현인 **SQLite 합성 네트워크** 상태입니다. 실망이나 Mininet 상태를 조회한 것으로 해석하지 않습니다.

## 결과 분석과 실행시간 비교

결과 분석 탭은 실제 저장된 진단·조치·검증 기록으로 다음을 정리합니다. 별도 유료 모델을 호출해 분석문을 만드는 방식이 아닙니다.

- 원인에서 결과까지: 진단 에이전트가 제시한 원인, 실제 적용·되돌림·거부된 조치, 서비스 검증 결과와 Memory 저장 여부.
- 전후 비교: 실제 변경 기록의 설정값과 같은 대상/지표의 KPI 관측값. 변경 전은 기록된 `get_kpi`, 변경 후는 완료된 DB의 read-only 조회 또는 대응하는 검증 값입니다. 대상이 다르거나 자료가 없으면 값 대신 **기록 없음**으로 표시합니다.
- 처리 결과: 정상 무변경, 복구, 추가 진단, 변경 거부, 롤백, 실패 및 중단을 구분합니다. `COMPLETED`와 서비스 복구 성공을 같게 취급하지 않습니다.
- 근거와 조건: Runbook/Memory 조건, 실제 검색·MCP·위임 횟수와 원본 근거 JSON을 확인합니다. 모델이 표시한 확신 정도는 실제 정답률로 해석하지 않습니다.
- 기록 검사: 실행 당시 저장된 무결성 결과와 hash 존재 여부를 표시합니다. 화면을 열 때 전체 파일을 다시 검사했다고 주장하지 않습니다. 중단된 부분 기록은 완료·봉인된 실행과 구분합니다.

실행별 비교 표에서 조건과 다음 시간을 확인합니다.

- **전체 시간**: 실행 시작부터 입력 준비·episode 실행·무결성 검사·ledger/usage 집계까지의 wall time. 최종 HTML 작성과 artifact hash 봉인 시간은 포함하지 않습니다.
- **강제 대기**: 여러 프로세스가 동시에 기다린 구간은 한 번만 계산한 대기 구간의 합집합입니다.
- **대기 제외 추정**: 전체 시간에서 강제 대기를 뺀 값입니다. 실제 No Delay 실행의 측정값을 대신하지 않습니다.

정확한 RAG/Memory 성능 비교에는 같은 모델·장애·Seed·반복·Top K를 두고 **No Delay**로 각각 실행하세요. 표의 문서 수와 조건 hash, `summary.json`의 `input_conditions`와 `timing`을 함께 확인합니다. 반복 episode는 같은 run 내부 Memory를 공유하고, 다음 run은 웹 목록에서 선택한 초기 Memory로 시작합니다.

Delay 제어 파일은 run 바깥의 `runtime/`에 있습니다. 실행 중 변경 이력과 실제 대기는 run 내부에 기록하며, 종료 후 Delay 기본값을 바꿔도 과거 run의 seal이 바뀌지 않습니다.

## 진행 기록 읽기

실시간 모니터링의 넓은 화면은 왼쪽 처리 흐름과 오른쪽 진행 기록을 나란히 보여줍니다. 진행 기록은 관측 시각 기준 **최신순**이며, 새 기록은 맨 위에 추가됩니다. 이전 기록을 스크롤해 읽는 동안에는 위치를 유지합니다. `최신 따라가기`를 껐다 켜면 맨 위로 돌아갑니다. 기록이나 모듈·화살표를 선택하면 아래의 `선택한 기록`에서 상세 정보를 펼쳐 볼 수 있습니다. 좁은 화면에서는 처리 흐름 아래로 기록을 배치합니다.
