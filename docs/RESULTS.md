# 실제 LLM 실험 결과: D0와 L1·L2·L3

[처음으로](../README.md) · [시나리오 설명](WIRED_SCENARIOS.md) · [현재 상태](STATUS.md)

2026-11-11에 완료한 **합성 유선망 authoring 실험**의 공개 요약이다. 상세 보고서·원시 대화·비용 장부·고정 소스 사본은 로컬 원본으로 보존하며 GitHub에는 포함하지 않는다. 아래 숫자는 실행 산출물을 대조한 과거 결과이며 이 문서를 작성하며 다시 API를 호출한 결과가 아니다.

## 1. 무엇을 시험했나

장애 신고를 받은 Operation Agent가 Diagnosis Agent에 원인 분석을 맡기고, 허용된 변경을 적용한 뒤 서비스 회복을 확인하도록 했다.

| 조건 | 값 |
|---|---|
| 기본 방식 | D0, `NullGate` — Protection 효과 비교 전의 기준 동작 |
| 모델 | 요청/응답 기록상 `gpt-6-luna` alias. 날짜가 고정된 snapshot ID는 아님 |
| 네트워크 | `wired-v1` / SQLite 합성 backend |
| 사례 | W1–W5/N0 6유형 × seed 1–5 = 난이도별 30건 |
| Runbook / Memory | RAG ON, 초기 Memory 0, Memory OFF |
| 인위적 지연 | No Delay. 모델 응답·도구·저장 시간은 여전히 발생 |
| 난이도 | L1 추가 알람 0개, L2 1개, L3 2개 |
| 통제 | 같은 fault/seed의 원인·정답 조치·초기 상태를 유지, 당시 동일 소스·모델 조건 비교 |

seed는 반복 조건을 재현하기 위한 번호다. 실제 API 호출은 외부 서비스 상태 등의 영향을 받으므로 seed가 같다고 응답 시간·문장이 완전히 같아지는 것은 아니다.

## 2. 시나리오와 실제 결과

| ID | 일반인 설명 | Agent가 해야 하는 일 | L1 / L2 / L3 목표 달성 |
|---|---|---|---|
| W1 | 길목의 장비가 고장 나 통신 길이 막힘 | 고장 장비를 유지한 채 정상 우회로 선택 | 각 5/5 |
| W2 | 사내 서버로 나가는 길 안내가 잘못됨 | 올바른 기본 게이트웨이 복원 | 각 5/5 |
| W3 | 회의 데이터 일부가 도중에 사라짐 | 해당 경로의 패킷 손실 설정 복원 | 각 5/5 |
| W4 | 파일 전송 속도 제한이 너무 낮음 | 대역폭 제한 복원 | 각 5/5 |
| W5 | 데이터가 가는 길에 불필요하게 지체됨 | 추가 지연 설정 복원 | 각 5/5 |
| N0 | 신고는 있었지만 측정 시점에는 정상 | 근거를 확인하고 변경 없이 종료 | 각 5/5 |

응답은 자유로운 설명 한 문장으로 끝나는 구조가 아니다. Diagnosis는 관측 근거와 원인·권고 조치를 구조화해 반환하고, Operation은 preview·승인·apply·verify 결과에 맞는 최종 report를 제출한다. **위 90건에서 진단은 정답과 일치했고 최종 report의 outcome은 검증 사실과 일치했다.** 원문 답변을 그대로 공개하지 않으며 이 문단은 관측된 행동을 요약한 것이다.

## 4. 방해 알람이 실제 전달됐는가

L2/L3는 관련 없는 다른 장비의 WARN 알람을 추가한다. DB에 알람이 존재하는 것과 Agent가 그 알람을 입력으로 받는 것은 다르다.

| 구분 | L1 | L2 | L3 |
|---|---|---:|---:|
| 생성한 추가 알람 | 0 | 사례당 1 | 사례당 2 |
| 실제 Diagnosis 입력 노출 | HTTP observer 미설치 | 8/30 | 12/30 |
| 노출 사례의 목표 달성 | 해당 없음 | 8/8 | 12/12 |

L2/L3의 나머지 40건은 Agent가 `HOST-001` 범위만 조회해 다른 장비의 알람이 제외됐다. L3 노출 12건에는 모두 2개가 들어갔다. L2/L3 API 496건의 metadata 관측과 usage request ID를 대조했다. L1은 추가 알람을 생성하지 않았지만 직접 관측한 HTTP 노출 0건으로 표기하지 않는다.

따라서 90/90 성공은 이 사례 집합에서 D0가 안정적으로 작동했다는 근거다. **전체 L2/L3 사례가 방해 정보를 읽고 이겨 냈다는 근거는 아니다.** 실제 노출된 20건의 결과와 범위 조회로 제외된 40건을 구분한다.

## 5. 수정 전 실패는 어떻게 처리했나

초기 L1 실행은 W1–W3 뒤 W4에서 최종 report outcome의 설명문이 계약과 맞지 않아 실패했다. 네트워크 복구와 진단이 맞아도 실행 실패로 보존했다. report schema·prompt·repair feedback을 명확히 하고 정확 일치 검사를 유지한 뒤 30건을 새로 실행했다. **수정 전 4건은 위 90건에 합치지 않았다.**

## 6. 다음 실험에 필요한 것

현재 표본은 6개 authoring 유형이며 정식 pilot·holdout 평가가 아니다. 다음에는 backend별로 조건을 고정하고 초기 Memory ON/OFF, 실제 노출을 보장한 방해 조건, 새로운 사례를 분리하여 평가할 수 있다. Mininet은 별도 adapter와 실제 probe 검증이 먼저 필요하다.

GitHub 준비 과정에서 경로·설치·문서·runbook README 제외 처리가 바뀌었다. 이 변경 이후 유료 90건을 재실행하지 않았으며 과거 고정 source와 현재 source가 동일하다고 주장하지 않는다. 현재 소스의 무료 회귀검사는 [VALIDATION](VALIDATION.md)에 기록한다.
